Tatami · Phase 1 · the pipeline as it stands

From JSON to Postgres

A 1.4 GB JSON corpus becomes four populated Postgres tables by way of generated OCaml. This replaces the earlier pipeline note, which described a design — Lean writing .sql, a shell script running COPY — that is no longer what the code does.

Generator Lean 4.33.0, no Mathlib Loader OCaml 5.5.0, pgx Corpus corpus/ci.json, 1.4 GB
01

Two programs, two passes

The corpus is read twice, by two different programs, for two different purposes. The first pass produces types; the second produces rows. Nothing is carried between them except the generated code.

02

Pass 1 — inference

Each document is observed from nothing and the results merged, rather than threaded through a shared accumulator. That is what makes the schema a property of the corpus and not of the order its documents arrived in.

  • Obs holds the set of types seen, not their running join. The join is taken once at the end, by Obs.joined. A type conflict is therefore found when the set is complete, and can name every type involved rather than the two that happened to meet first.
  • Nothing downstream sorts. That matters because Array.qsort has no correctness lemmas in core — not even that it returns a permutation of its input.
  • Reading is bounded. Stream.foldDocuments takes 1 MiB chunks and decodes only whole documents, so memory is a chunk plus one document plus the accumulator. Standard input is the exception: a pipe has no size to bound a loop with, so it is read whole.
  • orderTables is the load order. It topologically sorts the schema along the graph the foreign keys run down, so a table always follows the tables it points into — by construction rather than by care.
03

What gets generated

Three modules per table, and one registry. Loader is the only thing bin/load.ml talks to — which is why that file contains no table name, and adding a table to the corpus does not change it.

The loaders deliberately have no .mli, so Tatami.Schema.load_dir, which reads schema/*.mli as data, still sees four tables rather than nine. Every match in the registry has a default, so asking about a table that does not exist is answered rather than a crash.

04

Pass 2 — the walk

Three things the JSON does not carry are supplied here: the key of a document that has none, the key of the parent, and the position within a collection. They are exactly the three the layout marks as derived.

05

Where the generated modules do their work

Rows are not bound straight from JSON. Each row is built as a typed record through make, completed with setters, and read back out through the getters. The record is what reaches the database — pgx never sees the JSON.

(* schema/run_row.ml *)
let row ~self ~parent ~pos ~doc =
  let r = Run.make ~id:Neutral.int ~repo_id:Neutral.uuid ~idx:Neutral.int
            ~branch:(Json.string doc "branch") ~ms:(Json.int doc "ms")
            ~status:(Json.string doc "status")
            ~trigger:(Json.string_opt doc "trigger") in
  let r = Run.set_id      r (Unbind.int  self)   in
  let r = Run.set_repo_id r (Unbind.uuid parent) in
  let r = Run.set_idx     r (Unbind.int  pos)    in
  [Bind.int (Run.id r); Bind.uuid (Run.repo_id r); Bind.int (Run.idx r);
   Bind.string (Run.branch r); Bind.int (Run.ms r);
   Bind.string (Run.status r); Bind.string_opt (Run.trigger r)]

What the setters are actually for

Ten of the twenty-five generated setters are ever called, and they are the same three per table: set_id, set_<parent>_id, set_idx. Every member setter — set_name, set_branch, set_status — is dead, because member values go straight into make from Json.*. Nothing ever updates a loaded row. So make writes the data; the setters patch in the three values the walk knows and the document does not.

The record is a typecheck, not a carrier

It lives for one expression and is immediately destructured. Its value is that make is labelled, so a column that is missing, misnamed or of the wrong type fails at ocamlc rather than at insert. That is real, and it is most of what the .mli earns on this path — but it is a compile-time guarantee, not a runtime one.

06

Running it

There is no schema file to apply before loading. The tables, their columns, their nullability and their foreign keys are all derived from the corpus, and load.exe issues them over the same connection it loads on.

lake build
./.lake/build/bin/tatami CORPUS --config CONFIG -o schema   ; generate
./db/up.sh                                                  ; postgres container
./db/load.sh CORPUS                                         ; dune build, then load

The config is not checked in. Without one, table names are path-derived — root, runs, runs_jobs, runs_jobs_steps. The committed schema/ uses repo, run, job, step, so it was generated with a config that no file in the repository records. This one reproduces it exactly:

{ "root": "repo",
  "names": { ".runs[]":                     "run",
             ".runs[].jobs[]":              "job",
             ".runs[].jobs[].steps[]":      "step" } }

Verified: tatami corpus/small.json --config <above> -o <dir> produces files byte-identical to every one of the thirteen committed under schema/. Worth adding to the repository, since the committed OCaml cannot otherwise be regenerated.
