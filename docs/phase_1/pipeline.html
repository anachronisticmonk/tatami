Shredding to Postgres

How a 1.5 GB JSON corpus becomes four populated Postgres tables. Every stage below is built; the numbers are from running it end to end.

Measured on corpus/ci.json, 1.5 GB Checked with ocamlc 5.5.0 Status complete, loaded and checked
01

The binary

One command, two passes over the file, and one value — the Schema — that everything downstream is derived from.

tatami --config config.json --data -o out corpus/ci.json
02

Loading

The binary writes files and stops. Only psql touches the database, driven by a generated script — so connection details, Docker and psql availability stay out of the generator, and a failed COPY leaves something you can read and re-run.

Memory is constant, not proportional: 73 MB whether the input is 21 MB or 1.5 GB. Before streaming it was about forty-five times the input, which put the full corpus at roughly 67 GB. Loading is the generated load.sh against Postgres 16, and every foreign key resolved.

05

Two facts that decide the shape

The file is read twice

A row cannot be written until the schema is final, and a member first appearing in document 800,000 changes both the column set and its order. So pass 1 must finish before pass 2 starts. Nothing carries between them: keys are minted during pass 2 and nothing in pass 1 depends on them, which is what makes two passes cheap rather than awkward.

The Schema is the only hub

The .mli, the .ml, CREATE TABLE, the constraints and the column order the TSVs are written in all come from one value. That is what keeps the database a faithful second copy of the same data — today that agreement is maintained by hand, in a comment.

06

Before starting

  1. Do the generated .ml files have a job? Phase 3 parses the .mli text and never compiles anything we emit, and effects are cancelled, so nothing currently consumes them. They become the most important file we emit only if Root.get is meant to become a Postgres query.
  2. Table naming. Ours are path-derived — root, runs, runs_jobs, runs_jobs_steps. The filename becomes the SQL table name, so this decides the database too.
  3. Column order. Alphabetical today; document order is what makes schema.sql line up with the .mli, and what the existing test expects.
