#+TITLE: Tatami
#+SUBTITLE: JSON shredding and staged lowering to effect-typed OCaml

Shred JSON into a relational schema, generate typed OCaml modules from it, then
lower those modules until queries can be scheduled across CPU and GPU.

The design note is [[file:docs/design-note/tatami.pdf][docs/design-note/tatami.pdf]].

* Layout

A tatami mat is a woven face laid over a compressed core, bound at the edges by
a cloth border. The repository is split the same way, and the split is also the
ordinary compiler one: front end, back end, and the interface between them.

| Directory | Role                | Phases | Owner              |
|-----------+---------------------+--------+--------------------|
| ~omote/~  | 表 — the face       | 1, 2   | Vimala, Vishakh    |
| ~toko/~   | 床 — the core       | 3      | Durwasa            |
| ~heri/~   | 縁 — the border     | —      | shared, by consent |

** omote/ — front end

JSON in, OCaml modules out. Corpus reading, schema inference, shredding, module
generation (Phase 1), and the source-to-source rewrite of plain accessors into
effect-performing ones (Phase 2).

Specified by [[file:docs/phase_1/lowering.pdf][docs/phase_1/lowering.pdf]], which is complete and decided.

** toko/ — back end

Queries in, execution plans out. The OCaml-embedded query language,
distillation into fragments, the operator and join-implementation repository,
plan enumeration and costing, and CPU/GPU placement (Phase 3).

Notes in [[file:docs/phase_3/][docs/phase_3/]]. Nothing here is decided yet.

** heri/ — the border

What the two halves agree on, and nothing else: the schema representation, the
description of the generated module surface, and the effect signatures Phase 2
emits. Kept separate because Phase 3's central question — whether device
placement can be derived from the effect signature of an accessor rather than
from a cost model — makes that signature a load-bearing interface rather than an
implementation detail of either side.

* Working agreement

Dune enforces the direction: ~omote~ and ~toko~ both depend on ~heri~, and
neither can see the other. So a change confined to one side cannot break the
other, and the only file worth coordinating over is a change to ~heri/~ — which
wants both sides to agree before it lands.

* Build

#+begin_src sh
dune build          # the OCaml libraries
make -C docs        # the design documents
#+end_src

Requires OCaml 5 (effects), currently developed against 5.2.1.
