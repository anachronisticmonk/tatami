what is being compared

Two kernels answer the same query. plain has never read the signature: every value it gets back is text, and it re-parses that text each time it is asked anything. tuned has read orders.mli, so it knows qty is int and cannot be null, and stores it as a dense int array with no validity mask.

Both send the identical SQL to Postgres and get identical rows back. Both stream those rows rather than materialising a list first. The only variable is what the rows become in memory.

The figures below are frozen output from dune exec bin/bench.exe against 200,012 rows. A live run in the box at the bottom will not match them exactly — a laptop with a browser open is not a benchmark — and the difference between the two is itself worth seeing.

Columns added one at a time. The marginal cost of each is readable from the .mli before anything runs — and the most expensive column in the signature is the one whose type says string option, which pays three times over: wider on the wire, a mask to allocate, and a null branch per row.

The workload the claim actually needs. Shredding text into typed arrays only repays if something then runs over those arrays more than once. Each query below runs in memory, against data already fetched.
