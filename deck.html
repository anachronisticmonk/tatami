The problem

Querying JSON Is Slow. Querying Tables Is Fast.

A document has to be walked. A table can be scanned, indexed and joined. Getting from one to the other needs a schema, and the JSON never states one, so we derive it from the documents themselves:

  • The types. ms is an int, rate a float.
  • The nullability. Which fields can be missing, and which never are.
  • The tables. What it shreds into, and the references that hold it together.
The thesis

An .mli Is a Contract

A signature file sits on a boundary and says exactly what crosses it. That is the right home for an inferred schema, not a JSON-schema document some loader re-interprets at runtime.

Read it and you know the table:

  • its columns and their types;
  • that error is the only column that can be null;
  • that ms is int, not int option, because the data never lacked it;
  • of_job, the foreign key expressed as a function;
  • idx, the array position. A JSON array is a list; a SQL table is a set, so the ordering is lost on the way in. ORDER BY idx is what brings it back.
Why functional

Proved, Compiled and Executed

Lean 4 for inference and proof, OCaml for everything after. The .mli is the only thing that passes between them, and all three stages read the same one.

  • Lean 4 proves it, then writes it. For every corpus it accepts, the signature it emits is provably a description of that data: types principal, nullability exact, the table graph the same graph. The step from documents to a signature carries a theorem, not a test suite.
  • The generated .ml fills the tables. The same signature, compiled: it streams documents into four tables and pushes the rows into Postgres through pgx, parents and array positions intact.
  • The backend reads it again at run time. Schema.load_dir "schema" parses the .mli files as data and picks each column's physical layout from them, Plain or Nullable, Dense or Var. Nothing is special-cased by name.

Nullability

What Knowing Nullability Buys You

One bit per column, and it settles the entire physical layout.

The Signature Says int

  • Store the integers directly, dense and contiguous.
  • No mask array at all.
  • No check before a value: the loop reads, compares, moves on.
  • 8 bytes a row.
  • A run of rows can be copied or scanned as one block.

The Signature Says int option

  • Dense values, plus a parallel mask.
  • A missing value leaves the slot at its initialiser: 0 for an int, "" for a string.
  • Those bytes are identical to a real 0 or a real empty string.
  • A check before every value.
  • 16 bytes a row.

That is the mask's whole job: telling no value apart from a value that happens to be zero. When the type says the column is total, there is nothing left to tell apart, so the mask is never built.

The payoff

The Proof Is What Lets Us Delete the Mask

8 bytes an element against 24, but size is the smaller half. The dense array is walked; the boxed one is chased, and the next address is unknown until the current pointer lands.

Differential testing, not a theorem. Lean proves the schema; that the two stores answer alike is checked, not proved.

In conclusion

Columns beating rows on scans is not our finding.

Settled since MonetDB and C‑Store. Our numbers agree with it on some queries and not others, and agreeing with established results is not a contribution.

Everywhere else nullability is an input. Here it is an output.

Parquet and Arrow already drop the validity buffer for a non‑nullable field. But somebody asserts that flag, hand‑written or sampled and guessed, and nothing checks it, though it decides whether a bitmap exists for every row for the life of the data. We derive it from the documents and prove it exact, then hand it to the storage engine as an .mli that Lean proves, OCaml compiles, and the server parses at startup.

And the exactness survives being computed with.

A conservative analysis decays: maybe‑null combined with maybe‑null is maybe‑null, and a few operations deep everything is option again. Our leaves are generated exact, so ms × rate is total too and needs no mask of its own. That is why computed at 3.34× beats scan at 3.21× while doing strictly more work per row.
