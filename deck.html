The problem

Nobody wrote down what shape the data is

You are handed a pile of JSON — a CI service's build history. Repos hold runs, runs hold jobs, jobs hold steps. Four levels, every level an array, no declaration anywhere.

  • Optionality has two spellings: a field may be null, or simply absent. They mean the same thing.
  • The usual answer is to guess the schema, hand-write a loader, and discover where you guessed wrong in production.
  • A guess that says string where the data needs string option compiles cleanly — then dies on the first document missing that field.

So the question is not "can we infer a schema". It is: can we infer one we are entitled to rely on?

The thesis

An .mli is a contract

A signature file sits on a boundary and says exactly what crosses it. That is the right home for an inferred schema — not a JSON-schema document some loader re-interprets at runtime.

Read it and you know the table:

  • its columns and their types;
  • that error is the only column that can be null;
  • that ms is int, not int option — the data never lacked it;
  • of_job — the foreign key, expressed as a function;
  • idx — the array position, kept because order is information a table would otherwise lose.
Why functional

Two languages, one discipline

The pipeline is functional end to end. That is not a costume for the hackathon — it is what makes the central claim checkable.

Lean 4 — inference and proof

Inference is the one component whose correctness everything else rests on. In Lean it is not merely tested; it carries theorems. The generator and its proof live in the same language, so the thing proved is the thing that runs.

OCaml — loading, storage, measurement

The generated signatures are OCaml, so the contract is enforced by the compiler that builds the loader. Stores, queries and benchmarks are all OCaml — no imperative escape hatch in the middle.

The one place correctness truly had to be guaranteed is the one place we could hand to a theorem prover. Everything downstream is ordinary, typed, functional code that the contract holds together.

The proof

pipeline_correct, in five parts

221 theorems and lemmas, zero sorrys, composing into one top-level statement.

PartWhat it says
Well-formednessThe emitted signature is legal OCaml — no repeated module, value or field name.
CanonicityThe schema depends on the corpus as a set of documents, not arrival order. Shuffle the input and the output is equal, not merely equivalent — which is why two runs agree byte for byte.
Structure preservationThe tree the documents induce and the graph in the signatures are the same graph: no edge lost, none invented, distinct tables get distinct modules, and it is rooted — so no table is declared that the loader would create and never fill.
PrincipalityEvery field gets the least type admitting all values seen. Adequacy alone is nearly free — float describes integers, so does int option. Minimality rules the loose answers out.
NullabilityA column is optional exactly when some document lacked a value there.

It is worth saying what it does not claim: every part is conditional on inference and generation both succeeding, and it says nothing about rows — Lean describes the tables, OCaml fills them.

The proof · sharpest part

Why nullability had to be proved

The counts identity. Every visit to a table is accounted for at every field — a value, an explicit null, or an absence. Nothing else.

And the flag reads off it. A field is optional precisely when it carried a value fewer times than its table was visited.

This matters because absence is computed by truncating subtraction. Without the identity, a field some document omitted could report absent = 0, come out non-optional, and the generator would emit string where the data needs string option.

That OCaml compiles. The store does defend itself — a total column meeting a null aborts with step.error is NULL in the data, but its signature says otherwise — so it is a loud failure, not corruption. But it lands at load time, on production data, in code a theorem prover wrote and the compiler accepted. The theorem does not make the crash survivable; it makes the condition unreachable.

The payoff

The proof is what lets us delete the mask

What each column is comes from the .mli and from nowhere else.

  • A wrong option costs a mask, a branch and the memory to hold them — on every row, forever.
  • A missing option costs a crash on the first absent value.
  • Exactness is therefore not a nicety. It is the precondition for the layout being sound at all.

Measured: 264 MB columnar vs 297 MB row-major on the 200 MB corpus.

The measurements

Correctness before speed

Five queries, answered by three stores — raw Yojson, a row-major record store, and the columnar one. Every store implements the same signature, because a benchmark where each side answers a question shaped to suit it measures nothing.

All three stores return identical answers, on every corpus. Float sums are compared to a tolerance, because they are summed in a different order on each side; everything else is integral and must match exactly.

Only then are the timings worth reading.

The measurements · results

Which queries the types make faster

columnar faster row-major faster

We are not claiming to have built a faster database. Two of the five go the other way by design — document is the case a row store exists for. If columns won that one too, the benchmark would be wrong somewhere. The useful claim is narrower: once the type is known, you can predict which queries get faster — from the schema, before reading a row.

The measurements · selectivity

What a planner would want to know

Sweeping the predicate threshold — qty > n — across the same 50 MB corpus.

A U-curve. Highly selective predicates and full scans both do very well; the middle is where per-row branching costs most. This is exactly the shape a query planner would want — and the schema already says which columns are scannable and which are nullable, before a single row is read.

What is new here

Two claims, stated so they can be refuted

The proof is spent, not displayed

Machine-checked principality is old news — Algorithm W is mechanised in Coq, Isabelle and HOL4. JSON schema inference has paper proofs too (Baazizi et al.). What we have not found is the link between the theorem and the bytes: nullability is the licence to delete the validity mask from the layout, and the saving is measured.

OCaml has no columnar story

No Arrow binding, no Parquet reader, no columnar engine. pgx is excellent and gives you rows. If you want dense typed columns in OCaml today, you write them — so we did, driven entirely by generated types. The absence is the opportunity; the numbers are the argument for closing it.

Functional the whole way down: Lean 4 for inference and proof, OCaml for loading, storage, querying and measurement.
