#+TITLE: toko — 床, the core

The back end. Queries in, execution plans out. Phase 3.

* Scope

- The OCaml-embedded query language.
- *Distillation* — decomposing a query into fragments and annotating each with
  the execution targets it can legally be lowered to.
- The repository of join implementations and physical operators.
- Plan enumeration and costing over that repository.
- Device placement: which fragment goes to CPU, which to GPU.

* The question

The design note is deliberately thin here, and the part that is actually ours is
narrow. BOSS (Mohr-Daurat, Sun, Pirk, PVLDB 17(4):877–890, 2023) already builds
a query engine out of separable kernels dispatched per device at run time, and
Phase 3 adopts that decomposition wholesale. What is left is a compiler
question rather than a systems one:

#+begin_quote
Can the dispatch criterion be derived from the effect signature of the
generated accessors, rather than from a cost model?
#+end_quote

That is why ~heri/~ exists and why the effect signature lives there. If the
answer is yes, an accessor's signature is the input to placement, and the shape
of that signature is something the front end and back end have to agree on
rather than something either decides alone.

* Status

Nothing is decided. Open questions are being collected in
[[file:../docs/phase_3/notes.org][docs/phase_3/notes.org]], with the intent of eventually settling them the way
Phase 1 settled its own — one scenario at a time, options considered, one
selected, limitation recorded.
