Splitting generated.mli

We want one .mli per module instead of one file holding all of them. Referential integrity is what makes that hard, because the foreign key and the join form a cycle — and OCaml compilation units cannot be mutually recursive. Two ways out, both verified.

Checked with ocamlc 5.5.0 Files examples/split-mli/ Status nothing implemented yet
01

Why the file can’t just be cut apart

Today every module lands in one file, so module rec lets them refer to each other freely. As soon as the document contains a collection, those references form a genuine cycle:

(* generated.mli, as emitted today *)
module rec Xs : sig
  type t = { id : id; parent_id : Root.id; idx : int; n : int }   (* Xs → Root *)
end
and Root : sig
  val xs : t -> Xs.t list                                      (* Root → Xs *)
end

Xs names Root.id — that is the foreign key. Root names Xs.t — that is the join. The cycle is the referential integrity. It is fine inside one file and impossible across two, so splitting means deliberately removing one of the two arrows.

02

Cutting it apart unchanged fails both ways round

There is no ordering that rescues it. Each attempt fails on the half of the cycle the other one satisfied:

ocamlc -c b.mli xs.mli root.mli

File "xs.mli", line 2:
type t = { id : id; parent_id : Root.id; ... }
                                ^^^^
Error: Unbound module Root

ocamlc -c b.mli root.mli xs.mli

File "root.mli", line 5:
val xs : t -> Xs.t list
              ^^
Error: Unbound module Xs

Referential integrity holds either way

This is the thing worth checking, and it does not separate the two. Both consumers below were type-checked against the generated .cmi files under each option.

accepted ×2

08

What actually separates them

Option A

a shared ids.mli

  • Accessors stay on the parent, matching the design note’s §2.1 correspondence — joining on a foreign key becomes an accessor function.
  • Emit order stays deepest-first, which is the order tables already come out in. No new sorting code.
  • A foreign key into a nested object still reads b : B.id, exactly as the note writes it. Only collection back-references change.
  • Root.id stays usable everywhere — it is a transparent alias for the abstract Ids.root.
  • One extra generated file, and Ids becomes a reserved module name that a table called ids would collide with.

Option B

the accessor moves to the child

  • No extra file. Every id stays abstract inside its own module, exactly as now.
  • Xs.of_root reads like the query it lowers to — select * from xs where parent_id = ? — which may matter more for the Phase 2 work than it does here.
  • Root.xs r becomes Xs.of_root r.Root.id. The join reads from the child, which is the opposite of where the note puts it.
  • Emit order stops being deepest-first: nested objects order parent-after-child, collections order parent-before-child. Needs a real topological sort instead of the current length sort.
09

What we need to decide

  1. Where should the join accessor live — on the parent (Root.xs) or on the child (Xs.of_root)?
  2. Is one extra generated module, ids.mli, acceptable in the output?
  3. For the query-optimisation work: does Xs.of_root : Root.id -> t list carry more useful information than Root.xs : t -> Xs.t list, or less?

Everything here is hand-written to compare the two before either is built — nothing in Tatami/ has changed. Run examples/split-mli/check.sh to reproduce every result on this page.
